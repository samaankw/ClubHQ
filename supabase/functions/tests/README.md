# Edge function tests

Covers the recipient targeting and payload building in
`send-announcement-push`, extracted into `../_shared/announcementPush.ts` so it
can be exercised without an HTTP server or a Supabase project.

```bash
npm run test:functions      # deno test --allow-none supabase/functions/tests/
```

Needs [Deno](https://deno.com) on PATH. Nothing else — no network, no database,
no credentials, which is why `--allow-none` is safe to keep on.

## Why this half is tested and the rest isn't

The tests are written around the **cancellation notices** from migration 0035.
Every other announcement is typed by a human who can see who they're addressing
before they hit post. A cancellation is generated by a delete trigger and pushed
by a fire-and-forget call from `app/event/[id].tsx`, with nobody reading it
first — so targeting is the only thing between a deleted session and forty
misdirected phones, and it has no human check behind it.

The failures here are also all silent. Sending to the wrong club, or to nobody,
returns `200 {"sent": 0}`. There is no error to notice.

Not covered: the auth, rate-limit, and CORS wrappers, and the `fetch` to Expo.
Those fail loudly, so they're worth less than the effort of faking them.

## The fake client

`fakeSupabase.ts` is an in-memory stand-in for the PostgREST builder that
actually applies `.eq` / `.neq` / `.in` / `.not(col, "is", null)` and resolves
one-level embeds like `players(parent_id)`.

Handing the module pre-fetched arrays would have been less code, but most of the
realistic bugs are in the queries themselves — filtering on a null `team_id`,
dropping `.eq("enabled", true)`, forgetting to exclude the author. A fake that
applies filters catches those. It also records every query, so a test can assert
on the request shape and not just the result.

## Where the seams are

Recipient selection spans two layers, and each side is tested where it lives:

| Concern | Tested in |
| --- | --- |
| Who the notice is *addressed* to (`target_type`, `team_id`, player targets) | `supabase/tests/test_cancellation_notices.py` |
| Who that resolves to, and which devices get pinged | here |
| `author_id` matching the caller, so the push isn't rejected 403 | `supabase/tests/test_cancellation_notices.py` |

That third row is the one to keep an eye on. `send-announcement-push` refuses to
fan out unless `announcement.author_id` equals the caller
(`send-announcement-push/index.ts:55`). If the trigger ever attributed a notice
to `events.created_by` instead of `auth.uid()` — which is what the *change*
trigger in 0034 falls back to — cancellations by a coach who didn't create the
session would be written correctly and then silently 403. The notice sits in the
feed, no phone rings.

## These tests were checked by breaking the code

Passing tests prove nothing on their own. Each assertion here was verified by
mutating `announcementPush.ts` and confirming the suite goes red — dropping
`.eq("enabled", true)`, dropping the mute filter, dropping the token `Set`,
removing each author exclusion, unscoping the staff lookup from the club,
changing the batch window, changing the deep-link type.

Three mutations survived the first pass, and all three were gaps in the
fixtures rather than in the code:

- **token dedup** — siblings dedupe at the recipient level, so the token-level
  `Set` was never reached. Fixed by adding one household tablet registered by
  two different parents.
- **author exclusion in the parent branches** — no fixture had the cancelling
  coach also on the roster as a parent. Fixed by giving the coach a kid on the
  team he coaches.
- **club scope on the staff lookup** — there was no coach or director at another
  club for a cross-tenant leak to reach. Fixed by adding one.

If you add a branch here, mutate it and watch a test fail before trusting it.
